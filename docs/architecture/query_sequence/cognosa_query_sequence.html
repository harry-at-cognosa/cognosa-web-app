Cognosa Query Sequence

One question from the browser to the answer, across the SPA, app, Postgres, the rt workers, Qdrant, and the LLM

The web request ends at step 3. Everything after that is asynchronous: the doc_tasks row in Postgres is the only channel between the app process and the rt process, and its status column is the state machine the browser polls. The vector store shown is Qdrant; ChromaDB and pgvector follow the same path.

What the browser sees

The QueryDocuments page submits once, then polls the task by uuid on a timeout loop. Each poll returns the status, a status text, a percent derived from status divided by six, the answer so far, and once complete the retrieved documents from context_json rendered as sources. Polling stops when the status is 6 or negative.

Retrieval parameters in play

The group's VDB row carries the embedding model name, the Qdrant collection, a retrieval parameter set, and optional retrieval filters. The parameter set selects the LangChain retriever mode, one of similarity, mmr, or similarity with a score threshold, with k, fetch_k, lambda_mult, and score_threshold. The filters become a Qdrant payload filter so the search is restricted to matching metadata before similarity is computed.
